The stack: what each piece is for, and why that one

Every tool in a GitOps cluster and the reason it is there: MicroK8s, Flux, Traefik, MetalLB, Longhorn, 1Password and External Secrets, Kyverno, Falco, Trivy, Prometheus, Alertmanager, Grafana, Loki, Renovate, Ansible, ARC and an AI agent with read-only RBAC.

The tools

Running the cluster

ToolWhy this one
MicroK8s The distribution the nodes run, installed from a snap. Snap means the operating system's install and its upgrades are one mechanism, and a node is something I can rebuild from a playbook instead of a machine I have to keep alive.
Flux CD The only thing that writes to the cluster, and it is what makes the rest survivable: it reconciles continuously, so anything not in a merged commit gets reverted. That single property is why "the agent can try things" is a bounded risk rather than a hope.
Flux Operator Declares the Flux installation as a Kubernetes object, in git. Without it the bootstrap has a step I ran by hand, and a hand-run step is the one nobody can reproduce.
Dex Single sign-on for humans: the API server trusts it as an OIDC issuer and the dashboard signs in against it, so access is a token with an expiry rather than a client certificate copied between machines. It is served on a path, not a host root.
Kustomize and Helm How a directory becomes YAML. Overlays and pinned chart values, so the difference between two environments is a small diff rather than a branch of copy-pasted files.

Images

ToolWhy this one
Spegel A registry mirror made out of the cluster itself. Every node runs one and they hand image layers to each other, so a layer one machine has already pulled is served from a peer instead of being fetched from the internet again — on four nodes, the difference between getting an image once and getting it four times. Pinned to 0.7 line because 0.8 wants containerd 2.2 and MicroK8s ships 2.1.6.

Getting traffic in, and certificates out

ToolWhy this one
Traefik Ingress. Its own CRD puts routing, TLS and middleware in one object instead of three annotations, and one wildcard certificate in a single store serves every route — so adding a hostname is not also a certificate problem.
MetalLB Gives real LAN addresses for LoadBalancer services. Worth it because ingress then behaves like ingress, instead of me maintaining a tunnel or port-forwards on the router.
cert-manager Issues and renews. The failure I care about is an expired certificate, which looks exactly like an outage to everyone except me, so renewal has to be somebody else's job.
external-dns Publishes the DNS record from the same object that declares the route. Small, and it removes a manual step from every hostname I add.

Storage

ToolWhy this one
Longhorn Replicated block storage across the nodes, with no separate SAN to buy or maintain. It is the heaviest thing in here and I would still keep it: a node can die without taking a volume with it, and "the disk went with the machine" is a failure mode I have already had once. A version bump waits for explicit approval and a maintenance window, because it is the one component whose upgrade can leave a pod unable to start.

Secrets

ToolWhy this one
1Password Connect + External Secrets Operator The only path by which a secret value reaches a pod. Nothing is copied into git and the agent has no read path at all — it can see that a secret exists, not what is in it. One path in, because a second path is a leak nobody has found yet.
Stakater Reloader Restarts a workload when the secret it consumes changes. Without it the operator rewrites the Secret and a Helm-rendered Deployment never notices, which is the kind of bug that survives for months because nothing is wrong.

Keeping the agent honest

ToolWhy this one
Kyverno Admission policies, including two that watch the agent's own identity. It is the answer to the failure mode that actually worries me: not a malicious agent, but me widening its permissions by accident at the end of a long day. It refuses the change instead of reporting it, and the policies have fixtures in CI that must refuse.
NetworkPolicy Default-deny in both directions in every namespace. It is also the single most common cause of a connectivity bug I will ever chase, and the reason that bug is diagnosable is that the answer is a file in the repository rather than a guess about the prompt.

Observability

ToolWhy this one
kube-prometheus-stack Prometheus, Alertmanager and Grafana as one chart. I did not choose the pieces individually because what is actually portable is the rule format and the query language, and those live in this distribution's ecosystem.
Grafana Alloy + Loki Log shipping and storage. Alloy ships logs from every pod; Loki stores them and Grafana queries them.
blackbox-exporter Probes every published hostname from outside the cluster, so "is it up" is a measurement rather than an assumption. It is also the cheapest possible check that survives a certificate going stale in silence.
Trivy Operator Image findings delivered as Kubernetes objects. That is the whole reason: as CRs they query, alert, aggregate and get triaged like everything else, instead of living in a scan report somebody reads once.
Falco + falcosidekick Runtime syscall detection — what a process does after it starts, which admission and image scanning structurally cannot see. sidekick normalises the output into Alertmanager so runtime detections route and group through the same pipeline as everything else instead of arriving somewhere nobody reads.

Acting

ToolWhy this one
Hermes The agent. Read-only RBAC in the cluster and a GitHub App identity in git, so its only write is a pull request and the author of a change is never the same identity as the reviewer.
Redis One job: the dedupe gate on alert-driven agent runs. It holds a key per announced alert, which is what stops one standing alert from costing an agent run every hour, forever. A component this small is justified by the bill it prevents.
Actions Runner Controller Ephemeral CI runners: one per job, no accumulated state, and they are pods in the cluster the repository describes. That last part is the argument for it — CI is tested against production's network rules rather than a hosted runner's.
Runner toolcache warmer A local cache of the binaries required for CI, on every node. A runner exists for one job and is thrown away, so without this every run re-downloads its tools. Each binary carries a version stamp, so a bumped pin re-warms instead of the cache quietly serving the old release, and nothing lands in the cache until its checksum verifies.
Renovate Opens a pull request when a newer version exists, hourly, one version at a time. Small safe bumps — patch, digest, pin — it merges itself through its own App bypass. A minor, and the control-plane pieces, wait for me.
Crossplane Manages the repository rulesets and the GitHub webhook as Kubernetes objects, and Flux reconciles them like anything else. The merge gate on three repositories is a file here with a diff and a history, and a setting changed by hand in GitHub's UI is put back on the next reconcile.
Discord + ntfy The whole human interface. Channels rather than one feed, because a policy finding and a paging incident are different kinds of message and should not share a thread. Everything that posts in holds a single channel webhook — except the agent, which holds a bot token scoped to the channels it was granted.

The hosts

ToolWhy this one
Ansible Node configuration lives in the same repository as the manifests, and resolves its secrets at run time so nothing lands in git. The split that matters: the operating system is a machine problem and the cluster is a set of pinned versions, and people usually ruin both by treating them as one.

What I would do differently

  • I delivered with Helmfile first. It renders a set of Helm releases and applies them, which is fine while a person is the one running it. What it does not do is converge when nobody is: a failed apply, or a hand edit, stays that way until someone notices. Flux replaced it, and the difference is not a better tool for the same job — the apply step left the workflow entirely, because the cluster now reconciles itself. The stale references to Helmfile still scattered through the repository notes are proof that a migration does not finish when the manifests move.
  • Node configuration should be manageable anywhere. I reached for Semaphore late; the fleet's operating system should have been driven from something I can use from a phone, not only a laptop terminal.
  • I would have bought more GPU. I tried running the agent locally first on my 16GB card and ended up on a hosted model, which is a decision a bigger card could have avoided.
  • The distribution was a lateral move. I moved off one Kubernetes distribution and onto another, which cost days and bought nothing. Pick a distribution on its merits once.

The test I apply to any addition

If a component cannot be justified by a question I have actually asked, it does not get deployed. That is a slow way to build and it means the list stays short enough to still be read.
