Guardrails

Read-only, no secrets, and one policy that watches the agent itself

Five things stop this going wrong: permissions, secret access, networking, admission, and the fact that the agent can't merge its own changes. Each covers a different failure.

The default everywhere is deny. Anything it has was written down and reviewed, not left unwatched. Every access decision here is a file in the repository with a diff and a history.

Five controls, none load-bearing alone

They are independent on purpose. A single gate that mostly works is one bug away from nothing; five narrow ones are one bug away from four.

The merge gate

Control five isn't a file, so it can't be diffed. It is a setting on GitHub, written down here because a control nobody re-reads is a control nobody notices drifting.

SettingWhat it stops
Require a pull request reviewMerging without anyone reading the diff
Require a code owner approvalThe agent approving its own work
Dismiss stale approvals on pushReviewing a diff, then pushing more under that approval
Enforce for administratorsMe skipping my own rules, which is the one I'd skip first
Require up to date + linear historyConflicts resolved on an unread diff, and merge-commit soup

Required approvals is zero and that is not a hole: CODEOWNERS is a wildcard, so every file has an owner and every pull request needs one approval. The agent holds write access, but it is not the code owner, so it cannot supply the approval its own PR needs.

What CI proves — and what it doesn't

Three required checks gate the merge. All three are content gates, and none of them proves the change is correct — that is the review.

Lint

Malformed YAML caught before Flux tries to apply it.

Validate

Builds every Flux root with Kustomize, discovered from the sync files so new components are covered automatically.

Secret Scan

TruffleHog over the PR's commits, not its tip — a credential added and deleted in the same branch still fails.

Nothing validates against the live API. A Kustomize build proves the tree assembles, not that the cluster will accept it; a rejected field only shows up when Flux reconciles.

Reach, not authority

It canIt cannot
Read any workload, pod, log, event, PVC, policy or Flux status apply, patch, delete, edit — or run helm at all
Query metrics and logs, and read the alerting pipeline's own logs Read a secret value, exec into a container, port-forward, or mint a token
Push a branch and open a pull request Merge to the cluster repository, or change a repository setting

When it needs something it can't read, the answer is a reviewed job that reads it and logs a sanitised result — never a wider role.

Permissions: get, list, watch, nothing else

The ClusterRole has get, list and watch on what it needs and no write verb anywhere. Three omissions do most of the work:

  • No secrets. It can see that one exists and who references it. It can't read it, so the layer that would leak a credential holds no credential.
  • No pods/exec. Reading stdout is fine. A shell inside a container is not.
  • No token minting. It can't create a service account token and climb from there.

Two Kyverno ClusterPolicies watch the agent's own identity, for the case where it talks me into a bad change. One keeps its role read-only and its bindings limited to read-only roles. The other denies pods/exec, token creation and Secret writes made as the agent — the RBAC already withholds all three, so this holds if that RBAC is widened by mistake.

Why a policy and not just RBAC

RBAC says what is allowed. The policy says what stays allowed. A pull request that quietly adds pods/exec at the end of a long day is the change that undoes everything else.

Secrets: one path in, and the agent isn't on it

Values live in 1Password. External Secrets Operator pulls one declared item per need through an in-cluster bridge and syncs it into the namespace that needs it. Nothing is copied into git, and there is no second path, because a second path is a leak you haven't noticed yet.

The agent's own credentials follow the same rule with one extra step. Its identity is a GitHub App, so the author and the reviewer are not the same identity. The App key is mounted only into the containers that mint tokens: an init container mints one at start, a sidecar re-mints before expiry, and the agent reads a short-lived token from a shared directory. The durable key never enters the container the model drives.

Apps, not personal tokens

Every machine identity here is an app or a webhook, never a human credential copied into a container. That choice is most of the blast radius.

GitHub AppPersonal access token
LifetimeInstallation token expires in an hourMonths, unless someone remembers
ScopeOnly the repositories it is installed onEvery repository the human can reach, or a hand-picked subset that widens silently
IdentityIts own actor in the audit logIndistinguishable from the human
If leakedDies within the hour; revoke the installationLive until rotated, and nothing tells you it leaked

The same reasoning covers chat and mail: the agent posts through a webhook, not a bot account with channel access. There is no chat client in the container and no account to borrow. It can talk to one channel; it cannot read history, join anything, or act as anyone.

Where a token is still the answer

A repository under a different owner is outside the App's installation, so no installation token can reach it. That case gets a fine-grained token scoped to that one repository and two permissions, synced from the vault like everything else — and it is the exception, written down.

Networking: default deny, then a written exception

Every namespace is default-deny for ingress and egress. Nothing talks to anything until a policy says it may, and the exceptions are objects in git. The agent's egress is a short list: DNS, the API server, the alert webhook, and one host over 443 for git.

The trap that catches everyone

The API server is a host process, not a pod. A namespace selector will never match it, so a policy that looks correct allows nothing. It needs an explicit address block.

Intent, contents, behaviour

Three layers, each blind to what the others cover. That is the whole argument for running all three instead of picking the best one.

Admission

Sees intent — what a manifest asks for, before it exists.

Scanning

Sees contents — high and critical findings, only where a fix exists, so the report fits in a response.

Runtime

Sees behaviour — Falco on a curated rule set. Exemptions are scoped by process, parent and host, never by path or image.

Change flow

Three reasons a change shows up: something moved upstream, a machine needs patching, or I decide something should be different. All three are a reviewed diff. None is a login and a manual command.

The hosts

Node config is Ansible in the same repository: packages, kernel settings, the Kubernetes snap channel, mounts, accounts. Secrets resolve from the vault at run time. Security updates install unattended and reboot on a staggered timetable, one host at a time, ordered so quorum never drops — which is why a reboot is an annotation on a dashboard, not a page.

The versions

Nothing floats on latest. Charts, images, actions and CLI tools are pinned, and Renovate checks hourly and opens one pull request per bump. Renovate over Dependabot because it understands Helm values and Kustomize overlays, which is most of this repository.

The pod is disposable

Config and skills are re-seeded from git on every start, and work happens in a throwaway worktree per task. Nothing durable lives only inside the pod, so "restart it" is always safe. Its skills are files in a repository with a history, which is where most of the entries on Why came from.

The rule that came from breaking something

The agent may not change its own tooling — git config, credential path, deployment — without asking. It did once, mid-task, then couldn't recover itself. Everything about its own environment needs approval first, including when the change looks obviously correct.

A real one that fired

The alert-detector cron woke the agent at 04:00 because a plane-worker pod hit its memory limit. It read the live state, diagnosed the OOM, opened the memory bump, and a human merged six minutes later. Nobody was at the keyboard until the merge.
