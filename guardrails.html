Guardrails

Almost everything here is something the agent cannot do

None of this makes the model more careful. It makes the consequences smaller: no write verbs, no secret values, barely any network, and no way to approve its own work.

A real one that fired

The alert-detector cron woke the agent at 04:00 because a plane-worker pod had hit its memory limit. It read the live state, diagnosed the OOM, opened the memory bump, and a human merged it six minutes later. Nobody was at the keyboard until the merge.

That is the system working, and it is not the interesting part. The interesting part is what the agent could have done instead: delete the pod and hope, raise the limit in place, or read the credentials on the way past. What follows is why that was the only move available to it.

Five controls, none load-bearing alone

They are independent on purpose. A single gate that mostly works is one bug away from nothing; five narrow ones are one bug away from four. Every permission inside the cluster is a file in the repository, with a diff and a history.

The fifth control isn't a file, so it can't be diffed, and that is exactly how it drifts. The repository requires a review and a code owner approval, and enforces both for administrators: me skipping my own rules is the one I would skip first. Required approvals is zero, which looks like a hole and isn't, because CODEOWNERS is a wildcard. Every file has an owner, the agent is not one, and so it cannot approve the pull request its own change needs.

Reach, not authority

It canIt cannot
Read any workload, pod, log, event, PVC, policy or Flux status apply, patch, delete, edit — or run helm at all
Query metrics and logs, and read the alerting pipeline's own logs Read a secret value, exec into a container, port-forward, or mint a token
Push a branch and open a pull request Merge to the cluster repository, or change a repository setting

The left column is generous and the right one is not, which is the whole design. When the agent needs something it cannot read, the answer is a reviewed job that reads it and logs a sanitised result, never a wider role.

Permissions: get, list, watch, nothing else

The ClusterRole has get, list and watch on what it needs and no write verb anywhere. Three omissions do most of the work:

  • No secrets. It can see that one exists and who references it. It can't read it, so the layer that would leak a credential holds no credential.
  • No pods/exec. Reading stdout is fine. A shell inside a container is not.
  • No token minting. It can't create a service account token and climb from there.

Two Kyverno ClusterPolicies watch the agent's own identity, for the case where it talks me into a bad change. One keeps its role read-only and its bindings limited to read-only roles. The other denies pods/exec, token creation and Secret writes made as the agent. The RBAC already withholds all three, so this holds if that RBAC is widened by mistake.

Why a policy and not just RBAC

RBAC says what is allowed. The policy says what stays allowed. A pull request that quietly adds pods/exec at the end of a long day is the change that undoes everything else.

Secrets: one path in, and the agent isn't on it

Values live in 1Password. External Secrets Operator pulls one declared item per need through an in-cluster bridge and syncs it into the namespace that needs it. Nothing is copied into git, and there is no second path, because a second path is a leak you haven't noticed yet.

The agent's own credentials follow the same rule with one extra step. Its identity is a GitHub App, and the App key is mounted only into the containers that mint tokens: an init container mints one at start, a sidecar re-mints before expiry, and the agent reads a short-lived token from a shared directory. The durable key never enters the container the model drives.

Why not a personal token

The default is an app or a webhook, never a human credential in a container. The reason is narrower than general hygiene, and it is why the merge gate above works at all: an app is not me.

A personal access token is one line of setup and a great deal of trouble. In every log and every audit trail it is me — same actor, same reach, same permissions. It would let the agent act on repositories it has no business in, and it would let it approve its own pull requests, because the identity supplying the approval would be the code owner. The gate would still be there, with nothing behind it.

An App costs an hour of setup and buys three properties. Its installation token expires after one hour, so a leaked credential has a shelf life rather than a rotation date nobody remembers. Its scope is the repositories it is installed on, not everything I can reach. And it is its own actor in the audit log, which is what keeps "the agent wrote this" and "a human approved this" as two separate facts rather than one sentence.

The same reasoning covers chat: the agent posts through a webhook rather than a bot account, which is why the separation between channels on the alerting page is a property of the credential rather than a routing rule someone maintains.

Where a token is still the answer

A repository under a different owner sits outside the App's installation, so no installation token can reach it. That is the one place a fine-grained token is correct, and it is confined on purpose: one repository, two permissions, synced from the vault like everything else.

Networking: default deny, then a written exception

Every namespace is default-deny for ingress and egress. Nothing talks to anything until a policy says it may, and the exceptions are objects in git. The agent's egress is a short list: DNS, the API server, the alert webhook, and one host over 443 for git.

The trap that catches everyone

The API server is a host process, not a pod. A namespace selector will never match it, so a policy that looks correct allows nothing. It needs an explicit address block.

Intent, contents, behaviour

Three layers, each blind to what the others cover. That is the whole argument for running all three instead of picking the best one.

Admission

Sees intent — what a manifest asks for, before it exists.

Scanning

Sees contents — high and critical findings, only where a fix exists, so the report fits in a response.

Runtime

Sees behaviour — Falco on a curated rule set. Exemptions are scoped by process, parent and host, never by path or image.

The pod is disposable

Config and skills are re-seeded from git on every start, and work happens in a throwaway worktree per task. Nothing durable lives only inside the pod, so "restart it" is always safe.

The rule that came from breaking something

The agent may not change its own tooling — git config, credential path, deployment — without asking. It did once, mid-task, then couldn't recover itself. Everything about its own environment needs approval first, including when the change looks obviously correct.
