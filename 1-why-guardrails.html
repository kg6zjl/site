Why guardrails matter

The threat model: not a malicious agent, but me widening permissions by accident at the end of a long day.

The threat model

The failure mode that actually worries me isn't a malicious agent. It's me widening its permissions by accident at the end of a long day.

An agent that can merge its own infrastructure changes is an agent that can authorise its own widening. The one thing it must never be able to do is approve the change that gives it more room. That's why the admission policies on its identity exist as well as the merge rule: two independent ways of saying no.

A rule the model can be talked out of is not a control

Neither is a rule the credential could ignore. The agent holds write access to this repository, so it is allowed to approve its own pull request in principle. What stops it is the branch protection, not its permissions: it is not the code owner, so it cannot give the approval its own pull request needs.

What the agent can and cannot do

✓ It can

  • Read any workload, pod, log, event, PVC, network policy, Flux object or CRD status
  • Query metrics and logs directly, and read the alerting pipeline's own logs
  • Push a branch and open a pull request, including a one-off job that prints what it needs
  • Reproduce a failure by running the same request from a pod it controls

✗ It cannot

  • apply, patch, delete, edit — or run helm at all
  • Read a secret value, exec into a container, port-forward, or mint a service account token
  • Merge to the cluster repository, or change a repository setting
  • Reach the API server by any path outside its approved egress rules

When the agent needs something it can't read, the answer is a reviewed job in the repository that reads it and logs a sanitised result — never a wider role.
