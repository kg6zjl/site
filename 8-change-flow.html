Change flow: three ways in, one gate, two appliers

A version moved upstream. A machine needs patching. Or I decide something should be different. All three handled as code — a diff in the repository, reviewed.

Three different reasons a change shows up

A version moved upstream. A machine needs patching. Or I just decide something should be different. All three are handled as code — a diff in the repository, reviewed — and none of them is handled by logging in and manually running something.

One bad habit people reach for

Bundling several checks into one shell line trains whoever is reading to approve without reading. Splitting them is slower and that's the point.

The hosts: Ansible

Node configuration is Ansible playbooks in the same repository as everything else: base packages, kernel settings, the pinned Kubernetes snap channel, the kubelet's node address, the mounts, the accounts.

A run resolves its secrets from the vault at run time, so nothing lands in git. Security updates then install unattended, and the machines reboot to apply them on a staggered timetable — one host at a time, ordered so control-plane quorum never drops.

That last part is why a reboot is not an alert here. It's the patching mechanism working, and paging on it would just train me to ignore the pager. Reboots are annotations on the node dashboard instead, so an unscheduled reboot is obvious by looking rather than by waking me up.

A role there looks for what only a host can see: a CSI mount a storage volume left behind when it was recreated, which stops a new pod from starting while every health check upstream stays green. And the API server's own flags — including who it trusts to authenticate a human — are a playbook here rather than a manifest, which makes them one of the few changes a person runs rather than merges and forgets.
